# Как пользоваться стартером сайтов (Claude Code и Codex)

Памятка для нового клиентского сайта и дальнейшей работы с ним.
Шаблон: [site-starter-max-edition-claude](https://github.com/maksymm-ops/site-starter-max-edition-claude) — твой приватный
репозиторий. Он сделан на основе
[codex-nextjs-site-starter](https://github.com/maisjandesign/codex-nextjs-site-starter)
Маиса и работает и в Claude Code, и в Codex. Гайд сверен с шаблоном
6 октября 2026 года.

**Коротко:** создай отдельную копию шаблона для каждого сайта, открой её
в Claude Code или Codex, дай материалы клиента и точный кадр Figma или
скриншот. Агент (Claude или Codex) подготовит проект, соберёт страницы,
покажет их локально и проверит результат. Публикация — отдельный шаг.

Этот гайд написан для дизайнера, который поручает сборку сайта агенту.
Промпты одинаковые для Claude и Codex. Команды и устройство кода
запоминать не нужно: укажи результат, источник дизайна и границы задачи.
Дополнительные сценарии ниже — наши рабочие запросы; агент выполняет их
только при наличии нужных инструментов и доступа.

## Claude и Codex: что общее и что отличается

Один и тот же проект можно вести и в Claude Code, и в Codex: например,
дома в одном, на работе в другом. Папка, правила, навыки шаблона и
промпты общие.

| Что | Claude Code | Codex |
| --- | --- | --- |
| Правила проекта | Читает `CLAUDE.md`, который подключает `AGENTS.md` | Читает `AGENTS.md` сам |
| 4 навыка шаблона | Находит сам в `.claude/skills/` | Читает их по пути, как сказано в `AGENTS.md` |
| Общие навыки (`better-*`, `gsap-*` и другие) | Твои глобальные навыки Claude | Твои глобальные навыки Codex |
| Figma | figma-console + Figma Desktop с плагином Desktop Bridge; запасные — figma-bridge, затем официальный Figma MCP | То же, если они подключены в Codex |
| Проверка в браузере | chrome_devtools | chrome_devtools или встроенный браузер Codex |
| Независимое ревью после крупных этапов | Запускается сам: агент-проверяющий | Запускается сам: проверяющий внутри Codex, если поддерживается, иначе отдельный проход проверки |
| Генерация картинок | fal по твоим правилам | fal, если подключён; иначе агент попросит оригиналы |

Если чего-то из таблицы на компьютере нет, агент продолжит по правилам
проекта и скажет, что было недоступно. История чата между Claude и Codex
не переносится: перед сменой сохраняй состояние промптом 2а.

## Подготовить компьютер один раз

Это нужно один раз на каждом компьютере, а не для каждого сайта.

1. Node.js 22.14 или новее и npm.
2. Git и GitHub CLI (`gh`, программа для работы с GitHub из командной
   строки) с входом в твой аккаунт — тогда агент сможет создавать
   репозитории клиентов.
3. Figma Desktop и подключение figma-console с плагином Desktop Bridge.
4. Подключение chrome_devtools (браузер, которым управляет агент).
5. Общие навыки: `better-layout`, `better-typography`, `better-colors`,
   `better-writing`, `better-ui`, `accessibility`, `gsap-react`, `gsap-core`,
   `gsap-scrolltrigger`, `gsap-plugins`, `gsap-utils`, `variant`, `break`,
   `explain-interface`, `interface-review`.

Навыки и общие правила одинаковые на всех компьютерах. Их источник —
приватный репозиторий [max-agent-skills](https://github.com/maksymm-ops/max-agent-skills):
копия твоей настройки Claude. Codex ставит из него то же самое по
инструкции `CODEX-SETUP.md`. Полный комплект (шаблон, навыки, гайд) для
переноса лежит в папке `F:\.Projects\Site Starter`: `Claude/` и `Codex/`.

Проверку можно поручить агенту:

```text
Проверь, готов ли этот компьютер к работе со стартером сайтов: Node.js,
npm, Git, вход в gh, подключения figma-console и chrome_devtools и общие
навыки из README шаблона. Ничего не устанавливай без моего согласия.
Дай список: что есть, чего не хватает и как это поставить.
```

Настроить Codex так же, как Claude (один раз на компьютере):

```text
Склонируй мой приватный репозиторий https://github.com/maksymm-ops/max-agent-skills
(через gh) и выполни по шагам инструкцию из файла CODEX-SETUP.md.
Перед каждым изменением делай резервные копии, ничего не удаляй, секреты
в чат не выводи. Отвечай мне по-русски, в конце дай короткий отчёт.
```

Когда навыки или правила поменялись (Claude обновляет репозиторий сам):

```text
Обнови навыки и общие правила из max-agent-skills по CODEX-SETUP.md:
забери свежую версию, покажи, что изменилось, и установи изменения.
Сделай резервные копии. Отвечай по-русски, коротко.
```

## Словарь для дизайнера

Не нужно вставлять все эти слова в каждый запрос. Большинство технических
решений агент выбирает по существующему проекту. Тебе важнее объяснить,
что должно получиться и как ты будешь это проверять.

| Слово | Что это и зачем тебе |
| --- | --- |
| Вёрстка | Превращение макета в страницу, которую можно открыть и использовать. |
| Next.js | Основа, на которой собран сайт: помогает организовать страницы и их работу. Это не редактор вроде Figma. |
| App Router | Способ организации страниц и общих частей сайта в Next.js. Например, один общий хедер для нескольких страниц. Уже используемый подход обычно сохраняем. |
| Компонент | Повторяемый элемент в коде: кнопка, карточка, меню. Похож на компонент Figma; изменения общего компонента могут затронуть несколько страниц. |
| Адаптивная версия | Расположение элементов подстраивается под ширину экрана, а не просто уменьшается целиком. |
| Next Image / next/image | Элемент Next.js для изображений: помогает подобрать размер загрузки, отложить загрузку дальних картинок и заранее занять место под них, чтобы страница не прыгала. Автоматическое уменьшение файлов зависит от способа размещения сайта. |
| CMS | Панель, где клиент меняет контент: тексты, фотографии, новости. Подготовить структуру к CMS и подключить саму панель — разные задачи. |
| SEO | Подготовка сайта к поиску: понятные страницы, заголовки и сведения о них. Это не гарантия места в Google. |
| Метаданные | Сведения о странице: название вкладки, описание для поиска и данные для превью ссылки. |
| OG / Open Graph | Заголовок, описание и картинка для карточки ссылки в мессенджере или соцсети; показ зависит и от самого сервиса. |
| Alt | Текстовое описание значимой картинки для людей, которые её не видят. Декоративная картинка обычно не нуждается в описании. |
| Storybook | Отдельный каталог настоящих элементов сайта и их состояний. |
| Навык | Файл с инструкцией для агента, как делать определённую работу. Агент читает его только на нужном этапе. |
| MCP | Подключение, через которое агент управляет другой программой: Figma, браузером, генератором картинок. |
| figma-console | Основное подключение к Figma. Работает через плагин Desktop Bridge, запущенный в Figma Desktop. |
| chrome_devtools | Браузер Chrome, которым управляет агент: открывает сайт, делает снимки, меряет размеры. |
| AGENTS.md / CLAUDE.md | Правила проекта для агента. Codex читает `AGENTS.md`, Claude — `CLAUDE.md`, который подключает тот же `AGENTS.md`. |
| `?static` | Добавка к адресу страницы: анимации сразу показывают конечное состояние, удобно для снимков. |
| GSAP | Инструмент анимаций в этом паке. Не нужно устанавливать его заново в каждой задаче. |
| Сборка / build | Проверка и подготовка файлов к размещению. Успешная сборка не доказывает, что форма отправляет заявки или макет точно повторён. |
| Хостинг | Сервис, где размещён сайт, чтобы его открывали другие люди. |
| Домен | Адрес сайта, например client.com. Покупка адреса сама по себе не размещает сайт. |
| Deploy / деплой | Выпуск определённой версии сайта на хостинг. |
| Preview | Рабочая версия для проверки и согласования; может быть локальной или доступной по ссылке. |
| Серверная часть | Работа, которую выполняет сервер, например обработка заявки или проверка секретного ключа. Простая страница HTML сама этого не делает. |
| Переменные окружения / .env | Настройки для запуска: адрес CMS, ключ сервиса и другие значения. Настоящие секреты не загружают в GitHub; пример настроек должен быть без секретов. |
| Git | Инструмент истории изменений файлов проекта. Он не хранит автоматически историю чатов, доступы к сервисам или изменения в Figma. |
| GitHub | Место в интернете для репозитория и совместной работы. Само наличие файлов на GitHub не означает публикацию сайта. |
| Репозиторий | Проект с файлами и историей Git. Часто один клиентский сайт — один репозиторий. |
| Commit / коммит | Сохранённый снимок выбранных изменений. Сначала он существует на компьютере. |
| Push / отправка | Передача коммитов на GitHub. Если настроена автоматическая публикация, отправка в определённую ветку может выпустить сайт. |
| Pull / получение | Получение и включение изменений с GitHub в местную версию; при расхождениях может потребоваться разбор конфликта. |
| Clone / клонирование | Первая загрузка репозитория с историей Git на компьютер. ZIP — просто копия файлов без этой истории. |
| Ветка / branch | Отдельная линия изменений в том же проекте. Переключение ветки обычно меняет файлы открытой папки; это не вторая независимая папка. |
| main | Обычное название основной ветки. У проекта оно может быть другим. |
| Merge / слияние | Объединение изменений веток. При правках одного участка может возникнуть конфликт. |
| Pull request / PR | Предложение перенести изменения ветки в другую ветку с возможностью обсудить и проверить их. Это не обязательный шаг для каждого маленького изменения. |
| Конфликт | Git не смог автоматически совместить две версии одного участка. Агент должен разобраться по утверждённому результату, а не случайно выбрать одну. |
| .gitignore | Список файлов, которые Git обычно не добавляет. Уже сохранённый в истории файл этот список сам не удаляет. |

Для новых промптов сохраняй этот подход: сначала понятная задача, затем
нужный термин с коротким пояснением в скобках при первом упоминании.
Названия файлов и команд оставляй точными. В старых промптах непонятные
названия можно сверить с этим словарём — заучивать их не требуется.

## Когда использовать этот шаблон

- Ты делаешь новый сайт по макету Figma или скриншоту.
- Вам нужны анимации и единые стили для всех страниц.
- Ты хочешь отдельно просматривать кнопки, карточки и другие части сайта в
  Storybook (каталоге элементов сайта).

Шаблон рассчитан прежде всего на **визуальный образец**. Если ты хочешь
придумать дизайн с нуля, сначала подготовьте набросок, подборку примеров или
согласованное визуальное направление. Один текстовый бриф сам по себе не даёт
шаблону образца для сравнения.

## Какие навыки входят в комплект

«Навык» здесь — файл с инструкциями для агента: **как выполнить
определённый вид работы**. Это не кнопка на сайте и не отдельная
программа, которой нужно учиться тебе. Агент читает навык только на том
этапе, где он нужен.

**4 навыка самого шаблона** (лежат в проекте, в `.claude/skills/`):

| Навык | Простыми словами |
| --- | --- |
| `reference-site` | Как собрать сайт по Figma или скриншоту. |
| `starter-components` | Общие стили, компоненты, Storybook и проверка перед сдачей. |
| `gsap-next-motion` | Анимации шаблона: плавная прокрутка, появление блоков, кнопки. |
| `site-audit` | Отдельный аудит готового сайта — только по твоему запросу. Пишет отчёт и не меняет код. |

**Общие навыки** берутся из твоей глобальной настройки, а не из шаблона:
`better-layout`, `better-typography`, `better-colors`, `better-writing`,
`better-ui` (расположение, шрифты, цвета, тексты, детали), `accessibility`
(доступность) и навыки GSAP. `variant` (варианты блока), `break`
(проверка в сложных условиях), `explain-interface` (разбор эффекта) и
`interface-review` запускаются только по твоей прямой просьбе.

Навыки **не подключают автоматически** твой аккаунт Figma, генератор
изображений или хостинг. Для этих действий нужен отдельный доступ.

## Один раз на каждый новый сайт

1. Создай копию шаблона под клиента. Проще всего: открой
   [свой шаблон на GitHub](https://github.com/maksymm-ops/site-starter-max-edition-claude), нажми **Use this template → Create a
   new repository**, назови по проекту клиента, выбери **Private** и
   скопируй на компьютер. Или попроси агента сделать локальную копию
   командой `npm run new-project`.
2. Открой **новую папку** в Claude Code или Codex как отдельный проект.
   В её корне должны быть `AGENTS.md` и `package.json`.
3. Подготовь сведения о клиенте, тексты, логотип, фотографии, шрифты и
   ссылку на **конкретный кадр** Figma. Если Figma нет, приложи скриншоты
   компьютерной и, если есть, мобильной версии.
4. Отправь стартовый промпт ниже. Агент сам скачает пакеты сайта
   (`npm run setup`) и удалит демо-страницу шаблона (`npm run clean-demo`).
   Нужны Node.js 22.14 или новее и доступ к интернету.

**Не работай в самом шаблоне как в проекте клиента.** У каждого сайта
своя копия и свой репозиторий. Шаблон улучшаем отдельно.

### Если переносишь старый проект: сначала разбери материалы

Этот вариант включает **настройку нового проекта из пака и перенос контекста**
перед промптом 1. Если нужно только разобрать папку материалов без настройки
проекта, используй «Разобрать бэкап» в разделе глобальных сценариев ниже:
там установка зависимостей не входит в задачу.

Для настройки нового проекта укажи полный путь
к папке, куда ты сложил прежние брифы, решения, дизайн-файлы и другие
материалы. Открой в агенте именно папку нового проекта на основе шаблона.

### Что шаблон делает по умолчанию

Если не сказать иначе, агент сделает так:

- **Анимации:** плавная прокрутка на компьютере, заголовки и блоки
  «выезжают» снизу, у кнопок поднимается заливка, текст прокручивается,
  стрелка уезжает. На телефоне прокрутка обычная — это не ошибка. Если в
  системе включено «уменьшение движения», анимаций нет. Хочешь спокойнее —
  напиши в промпте.
- **Заголовки:** все заголовки одного уровня на сайте одинаковые. Если в
  макете два разных размера H2, шаблон сведёт их к одному или уточнит,
  не другой ли это уровень.
- **Размеры текста** меняются ступенями (компьютер, планшет, телефон),
  а не плавно. Основной текст не мельче 16 px; если в макете мельче, это
  записывается как согласованное отклонение.
- **Скриншот вместо Figma:** агент сам меряет масштаб, цвета и строки
  текста (`npm run measure-ref`). Называй файлы с шириной экрана:
  `desktop-1440.png`, `mobile-390.png`. Скриншот с ретина-экрана в 2 раза
  больше — скрипт это учтёт и предупредит, если ширины не сходятся.
  Недостающие фото агент сделает только «похожими», оригиналы лучше прислать.
- **Проверка:** агент сравнивает с макетом по цифрам на ширине макета и на
  1440, 768, 390 и 320 px. Для снимков открывает страницу с `?static` —
  так анимации не прячут текст.
- **Кнопки:** форма меняется настройками (круглые, без стрелки, акцентные),
  без переписывания кода.
- **Чек-лист задачи:** для задач из нескольких шагов агент ведёт список в
  `design/status.md` и отмечает пункты по мере готовности. Найденное по дороге
  он записывает в раздел «ждёт решения Макса» и без твоего «да» не делает.
  Если задача разрастается или что-то мешает — останавливается и спрашивает.

## Куда попадает информация

| Что это | Где хранится | Что помнить |
| --- | --- | --- |
| Задача, страницы, язык, источники, неизвестное | `design/brief.md` | Это рабочий бриф, а не готовая страница. |
| Изображения, шрифты и их происхождение | `design/assets.json`; сами файлы в `public/assets/` | Указывается, что взято из Figma, а что создано или заменено. |
| Текущее состояние: что готово, что дальше | `design/status.md` | Обновляется в конце каждого этапа; с него начинает новый чат. |
| Важные решения и отклонения от макета | `design/decisions.md` | Например, округление размеров или замена недоступного шрифта. |
| Общие цвета, шрифты, размеры текста и отступы | `src/styles/tokens.css` | Это практическая основа дизайн-системы сайта. |
| Страницы и их содержимое | `src/app/` | Обновление одного брифа само по себе не меняет страницу. |
| Повторяющиеся элементы | `src/components/` | Например, кнопки и карточки. |
| Примеры элементов | `src/stories/` и `.storybook/` | Storybook должен показывать те же элементы, что и сайт. |
| Результаты обычной проверки | `verification/` | Скриншоты, проверенные размеры экрана и известные ограничения. |
| Отдельный аудит по твоему запросу | `site-audit/` | Отчёт об ошибках; аудит сам исходники не исправляет. |

Это **встроенные места именно этого шаблона**. Отдельной анкеты клиента,
панели управления контентом или автоматического переноса сведений из
документа на сайт здесь нет. Если у тебя большой объём исходных материалов,
можно попросить агента создать отдельную папку для них и указать её в брифе.

чата агента. Новому чату нужны сохранённые решения и состояние работы.
Полная стенограмма обычно не нужна. Если важное обсуждение осталось
только в другом чате, отдельно сохрани его выводы или доступный экспорт
в папку проекта. Агент не должен утверждать, что прочитал недоступный чат.

```text
Подготовь этот проект к продолжению на другом компьютере через SSD.
Сначала проверь текущее состояние файлов и незавершённой работы.

Сохрани контекст в рабочих документах: цель и требования, утверждённые

сделанное, незавершённое, ограничения и следующий шаг. Используй
design/brief.md, design/decisions.md и карту системы, если она есть.
Обнови design/status.md.

В заметке о продолжении укажи дату, текущую ветку и сохранённое состояние
изменений, если проект использует Git. Запиши последние фактические
проверки, их результат и ссылки на отчёты. Отметь, что утверждено,
а что только реализовано. Не придумывай историю отсутствующих чатов.

Проверь ссылки на материалы: изображения, шрифты, исходные документы,
локальные HTML-примеры. Найди зависимости от файлов вне папки проекта
и абсолютных путей старого компьютера. Нужные доступные материалы
скопируй внутрь проекта, сохранив оригиналы и происхождение, и обнови
ссылки. Для рабочих материалов используй относительные пути там,
где это возможно. Недоступные файлы перечисли как ограничения.

Укажи, что установить и подключить на новом компьютере: версию Node.js,
инструменты Figma, браузера и другие реально используемые подключения.
Для секретных настроек перечисли только названия переменных и способ
их безопасного восстановления; значения не включай в отчёт.

Не коммить и не публикуй изменения автоматически. Не удаляй файлы.
Проверь, что следующий чат сможет найти материалы по сохранённым ссылкам.
```

После отчёта останови запущенные серверы сайта и Storybook, дождись
завершения записи файлов и скопируй папку проекта со скрытыми папками.
Нужны исходники, `design/`, материалы, `public/`, `tooling/`, `scripts/`,
файлы инструкций, `package.json` и `package-lock.json`. Сохрани `.git`,
если нужна история изменений. Отчёты `verification/` и `site-audit/`

**Для переноса действующего проекта не используй `npm run new-project`.**
Эта команда создаёт чистый новый проект и исключает, в частности, историю

проверь отдельно файлы, которые не отслеживаются: шаблон исключает отчёты

переносит и их, если они есть и скрытые файлы тоже включены.

`node_modules`, `.next` и `storybook-static` — установленные пакеты и
результаты сборки; переносить их необязательно, они создаются заново.
Даже если скопировал их, не считай их проверенными для нового компьютера.
Файлы `.env` могут содержать ключи: восстанови их отдельно безопасным
способом, если проект их использует. Наличие папки не даёт новому агенту
автоматического входа в твой аккаунт или доступа к Figma.

### Промпт 2в. Продолжить перенесённый проект на другом компьютере

Открой перенесённую папку как проект в Claude Code или Codex на новом компьютере и отправь
этот промпт. Подготовка должна восстановить окружение, затем остановиться
с отчётом; она не означает автоматическое начало следующего этапа дизайна.

```text
Этот существующий проект перенесён с другого компьютера через SSD.
Сейчас восстанови контекст и подготовь окружение для продолжения.

Прочитай AGENTS.md, design/brief.md, design/decisions.md,
design/status.md, список материалов и карту дизайн-системы, если они есть.
Пройди по ссылкам на актуальные источники и отчёты в этих документах.
Если важной заметки или файла нет, отметь пробел и восстанови только
то, что подтверждается доступными файлами. Не считай всю историю чата
перенесённой вместе с папкой и не придумывай отсутствующие решения.

Проверь текущие файлы, ветку и незавершённые изменения, если есть Git.
Проверь Node.js и npm, затем выполни npm run setup в новой папке.
Сохрани клиентские материалы и мои изменения.

Проверь устаревшие абсолютные пути и наличие нужных файлов. Проверь,
какие подключения Figma и браузера действительно доступны здесь.
Не переноси глобальные настройки и разрешения со старого компьютера.
Отдельный аудит сайта сейчас не запускай.

После успешной настройки проверь обе сборки, запусти сайт и Storybook
и проверь их в браузере, если есть доступный инструмент. Если инструмент
недоступен, сообщи, что визуальная проверка не выполнена.
Обнови заметку о продолжении с новым расположением и результатом проверок.

В конце кратко объясни, что ты понял о проекте, что уже утверждено,
где остановилась работа, что готово на новом компьютере и какой следующий
шаг. Отдели старые результаты проверок от выполненных сейчас.
После отчёта остановись и дождись моей задачи на продолжение.
```

Пакеты сайта (`node_modules`) на новом компьютере лучше скачать заново:
это делает `npm run setup`.

Работай последовательно в одной актуальной копии. После работы на новом
компьютере снова сохрани состояние промптом 2а перед обратным переносом.
Если обе копии редактировались независимо, сначала сравни изменения;
перезапись папки целиком может потерять одну из версий.

### Промпт 3. Обновились сведения о клиенте или тексты

```text
Клиент прислал новую информацию: [вставь текст или укажи файл/ссылку].
Статус этой информации: [утверждено клиентом / рабочий вариант / пока
неизвестно]. Сравни её с текущим design/brief.md и содержимым сайта.
Обнови бриф и те страницы, на которые информация действительно влияет.
Если новые сведения противоречат старым, покажи противоречие; не придумывай
решение. Не публикуй на сайте неподтверждённые факты как проверенные.
После изменения перечисли, где именно обновился сайт, и проверь результат.
```

**Важно:** изменение `design/brief.md` сохраняет знание для следующих
задач, но не меняет видимый текст само по себе. Попроси обновить и страницы.

### Промпт 4. Добавить или заменить референс

```text
Добавляю референс: [ссылка, файл или скриншот]. Он нужен для [структуры
страницы / шрифта / цвета / анимации / отдельного блока]. Его статус:
[утверждённое направление / идея для изучения]. Изучи его, зафиксируй в
design/brief.md, что именно мы берём за ориентир, и обнови
design/decisions.md, если принято новое важное решение. Не копируй чужой
сайт целиком и не заменяй уже утверждённый дизайн без моего указания.
Рабочую идею сначала сохрани как вариант. Применяй её к сайту только если
я явно попросил реализацию и указал область изменений: [страница/блок].
```

Если ты заменяешь основной макет, так и напиши: «Это новый утверждённый
основной макет; старый больше не используем как цель сравнения».

### Промпт 4а. Подготовить изображения и шрифты

**Когда использовать:** Есть фотографии, логотипы и шрифты, которые нужно правильно подключить.

**Что приложить:** Папку с оригиналами и макет, где видно их использование.

```text
Подготовь материалы из [папка] для страниц [список].
Используй предоставленные оригиналы. Проверь шрифты, начертания, качество
изображений и нужные обрезки по утверждённому макету [ссылка].
Сохрани рабочие файлы по правилам проекта и обнови design/assets.json:
откуда взят каждый материал, где он используется, что является временной
заменой. Не меняй геометрию логотипов и SVG. Если оригинала нет, обозначь
нехватку; не выдавай похожий шрифт или картинку за точное совпадение.
Проверь затронутые страницы и обнови связанные примеры Storybook, если они есть.
```

**Что должно получиться:** Подключённые материалы и список оставшихся замен. Генерация картинок требует отдельного инструмента.

### Промпт 5. Обновить дизайн-систему

```text
Обновляем общие правила дизайна. Новое утверждённое решение:
[цвета, шрифт, заголовки, отступы, кнопки или ссылка на Figma].
Сравни его с текущим src/styles/tokens.css и реальными компонентами.
Обнови общие настройки, затем затронутые компоненты и их примеры в
Storybook. Проверь, что изменение последовательно видно на всех страницах,
в Storybook. Запиши важные отклонения в design/decisions.md.
Если правило шаблона «шаг 8 пикселей» мешает утверждённому дизайну,
сообщи конкретный конфликт и предложи решение.
```

Здесь «дизайн-система» — общие настройки и повторяющиеся элементы.
Например, если поменять основной цвет в одном месте, все кнопки, которые
используют этот цвет, должны измениться вместе. Если отдельная кнопка
оформлена вручную, агент должен найти и привести её к общему правилу.

### Промпт 5а. Обновить дизайн-систему по утверждённым страницам

Используй этот промпт, когда ты или клиент уже утвердили конкретную версию
страницы и её решения нужно применять на следующих страницах.

- **Утвердили новый концепт или главную страницу.** Обнови существующую
  систему по ним. Если системы ещё нет, начни с промпта 5б.
- **Утвердили дополнительную страницу.** В систему добавляются новые
  переиспользуемые элементы и согласованные варианты существующих.
- **Клиент утвердил правки на работающем сайте.** Сайт становится источником
  этих изменений; по нему обновляются библиотека Figma и общие элементы.
- **Клиент утвердил правки в Figma.** Макет становится источником изменений;
  по нему обновляются общие стили, компоненты сайта и Storybook.

Перед отправкой укажи конкретные страницы и версию, которую утвердили.
Если нужны обе среды, добавь ссылку на страницу дизайн-системы в Figma
и путь к проекту сайта. Если библиотека Figma ещё не создана, укажи файл,
в котором её нужно собрать на отдельной странице.

```text
Эти страницы утверждены: [ссылки на Figma или страницы сайта].
Обнови дизайн-систему на их основе.

Утверждённый источник изменений: [Figma / работающий сайт / HTML-файл
с полным путём]. Дизайн-система Figma: [ссылка на библиотеку или файл,
где нужно создать отдельную страницу]. Проект сайта: [путь].
Нужный результат: [обе среды / только Figma / только сайт и Storybook].

Перенеси новые переиспользуемые элементы и согласованные изменения
в общие стили, компоненты и Storybook, а также в дизайн-систему Figma
в соответствии с выбранным результатом.
Используй указанную утверждённую версию как источник изменений.

Запиши, что обновлено и где. Если Figma и сайт расходятся, а из моей
задачи непонятно, какая версия утверждена, уточни это перед переносом.

В Figma используй настоящие переиспользуемые компоненты и общие стили.
В коде используй общие настройки и компоненты проекта. Если переносишь
дизайн из отдельного HTML-файла, адаптируй его к структуре этого проекта.
Проверь результат в обеих доступных средах и затронутые страницы.
Отметь, если общее изменение затронуло другие страницы. Сохрани важные
решения в design/decisions.md. Сообщи, если часть работы не удалось
выполнить из-за отсутствия доступа или материалов.
```

После этого новые страницы можно поручать так: «Собери страницу по
утверждённой дизайн-системе проекта, используй существующие элементы».
Чтобы это стало постоянным правилом, отдельно попроси агента записать
расположение дизайн-системы и правило её использования в `AGENTS.md`
конкретного проекта. Наличие этого промпта в гайде само по себе правило
в проекте не меняет.

Обновлять систему после каждого изменения текста обычно не нужно.
Промпт нужен для общих визуальных правил и повторяющихся элементов.
Для экспериментального варианта сначала закончи согласование. Элементы
и состояния, которых нет на утверждённых страницах, требуют отдельного
решения: одна главная страница не определяет всю будущую библиотеку.

Этот сценарий расширяет штатный процесс шаблона работой с библиотекой
Figma. Для неё нужен доступ агента к файлу и возможность редактирования.
Синхронизация выполняется по задаче, автоматического обмена между
Figma и сайтом этот гайд не подключает.

### Промпт 5б. Создать первую дизайн-систему из концепта

Используй, когда концепт, главная страница или HTML-пример уже утверждены,
а набора общих правил и элементов ещё нет. Выбери результат: Figma,
компоненты сайта со Storybook или обе среды. Для твоего дальнейшего
процесса удобен последний вариант, если инструменты позволяют его сделать.

```text
Создай первую дизайн-систему из утверждённого источника:
[кадр Figma / страница сайта / полный путь к HTML-файлу].
Нужный результат: [Figma / код и Storybook / обе среды].
Файл Figma для библиотеки: [ссылка]. Проект сайта: [путь].

Прочитай правила проекта и выполни обязательную подготовку. Проверь,
какие инструменты доступны для чтения и редактирования Figma и проверки
сайта. Изучи источник визуально, а при наличии доступа — его структуру
и реальные значения стилей. Сохрани исходник.

Выдели общие цвета, шрифты, размеры текста, отступы и повторяющиеся
элементы. Используй уже существующие компоненты, если они подходят.
Отдели утверждённые решения от предложенных дополнений. Состояния,
которых нет в источнике, например ошибка формы, не считай утверждёнными.
Запиши конфликты с правилами шаблона и принятые решения.

Для Figma собери отдельную страницу дизайн-системы с общими стилями
и настоящими компонентами. Для сайта подготовь общие настройки,
повторяющиеся компоненты и их примеры в Storybook. Согласуй названия
элементов между средами. Существующие страницы меняй только там,
где это необходимо для выделения компонентов; сохрани их оформление.

Сохрани короткую карту системы: где лежат стили и элементы, какому
компоненту Figma соответствует компонент сайта, что утверждено,
а что ещё требует решения. Используй существующий подходящий документ;
если его нет, создай design/system.md и свяжи его с design/brief.md.
Проверь результат в выбранных средах. Сообщи, что готово и чего не хватает.
```

`design/system.md` — предложенная карта системы, а не штатный файл пака.
Она помогает агенту найти нужные элементы, но не заменяет компоненты Figma
и код. Отдельный HTML-пример может показывать утверждённый вид; его
структуру при переносе в проект иногда нужно переработать.

### Промпт 5в. Закрепить использование дизайн-системы

Используй один раз после создания системы и повторно, если изменились её
расположение или правила. Промпт редактирует инструкции конкретного
проекта; глобальные навыки и настройки агента для этого не нужны.

```text
Закрепи использование утверждённой дизайн-системы в AGENTS.md этого
проекта. Прочитай текущий файл и добавь короткое правило со ссылкой
на карту системы и библиотеку Figma: [ссылки/пути].

При создании страниц сначала использовать существующие общие стили
и компоненты. Новые элементы помечать рабочими вариантами до согласования.
Каталог компонентов сайта поддерживать при их создании, как требует
шаблон. Перенос утверждённых решений между сайтом и Figma выполнять
по моей явной задаче с указанным источником. Если он не определён
и версии расходятся, уточнить его. Покажи внесённое правило.
```

### Промпт 5г. Точно повторить размеры утверждённого макета

**Когда использовать:** Правило пака о размерах, кратных 8 пикселям, мешает повторить утверждённый дизайн.

**Что приложить:** Точный кадр Figma или HTML с доступными размерами; укажи страницы и элементы.

```text
Для [страницы или элементы] утверждённым источником является [кадр Figma
или HTML]. Разрешаю сохранить его реальные размеры, даже если они не кратны 8.
Сначала покажи расхождения с правилом пака. Зафиксируй ограниченное исключение
в правилах проекта и журнале решений. Согласуй общие роли текста и повторяемые
элементы; внеси только необходимые исключения в проверку дизайна.
Не отключай проверку целиком. Если доступны только скриншоты, обозначь размеры
как оценку, а не точные измерения. Проверь результат по источнику и в браузере.
```

**Что должно получиться:** Явное исключение для конкретного дизайна и работающие проверки остальных правил. Это осознанная адаптация пака.

### Промпт 6. Добавить страницу или раздел

```text
Добавь [страницу/раздел] для [цель]. Содержание и материалы: [текст,
ссылки, изображения]. Используй существующие стили и компоненты там, где
они подходят. Если нужен новый повторяющийся элемент, создай его один раз
и добавь пример в Storybook. Проверь вид на компьютере и телефоне, ссылки,
кнопки и результат сборки. Обнови design/brief.md, если изменилась
структура сайта.
```

### Промпт 6а. Собрать дополнительную страницу в Figma

Используй, когда сначала нужен редактируемый макет для согласования.

```text
Собери макет страницы [название] в файле Figma [ссылка].
Структура и тексты: [материалы]. Размеры экрана: [компьютер/телефон].
Используй утверждённую дизайн-систему [ссылка на библиотеку/карту].
Прочитай контекст проекта и проверь доступ к редактированию файла.

Применяй общие стили и экземпляры существующих компонентов. Если нужен
новый элемент, создай его как рабочий вариант с понятным названием.
Собери редактируемые блоки с настройками расположения, проверь длинные
тексты и поведение на заданных размерах. Покажи результат и новые
предложенные элементы. Сейчас нужна работа только в Figma.
```

После утверждения макета можно поручить его сборку на сайте промптом 6
и обновление общей системы промптом 5а. Возможность создавать макеты
зависит от доступных инструментов Figma; одного доступа на чтение мало.

### Промпт 6б. Внести правки клиента с понятным масштабом

Используй для конкретного списка правок. Укажи, какие из них касаются
одной страницы, а какие должны действовать везде.

```text
Внеси утверждённые правки клиента: [список].
Сейчас меняем [Figma / сайт]. Страницы: [ссылки/названия].
Только для этих страниц: [правки]. Общее для всего проекта: [правки].
Сохрани утверждённые тексты дословно там, где это требуется.

Проверь, какие общие компоненты затронуты. Если правка одной страницы
может изменить другие через общий компонент, уточни масштаб до её
применения. Внеси правки, проверь результат и запиши важные решения.
В конце перечисли изменённые страницы и отметь, нужна ли синхронизация
второй среды или обновление дизайн-системы.
```

После утверждения результата перенеси общие решения во вторую среду
промптом 5а. Исправление опечатки само по себе такого переноса не требует,
если вторая среда уже содержит правильный текст.

Используй, когда утверждён только вид для компьютера. Версия для телефона

### Промпт 10в. Выбрать способ размещения сайта на Next.js

**Когда использовать:** Выбираешь, где будет работать клиентский сайт.

**Что приложить:** Проект, нужные функции, желаемый сервис и ограничения
клиента по оплате или обслуживанию, если они уже известны.

```text
Изучи сайт [папка] и предложи способ размещения под его реальные функции:
[CMS, форма, личный кабинет или «обычные страницы»].
Проверь, нужен ли работающий сервер или достаточно статических файлов
(заранее собранных страниц). Учти Next Image, обработку форм, обновление
контента и другие используемые возможности. Не меняй проект ради GitHub Pages
без объяснения ограничений: этот сервис размещает статические файлы.
Если подходит GitHub Pages, покажи нужную подготовку и ограничения; иначе
предложи подходящий способ. Актуальные условия и стоимость проверь по источнику.
Объясни варианты простыми словами: что получу, как обновлять и что оплачивать.
Отдельно выясни, выпускается ли сайт автоматически при отправке в main.
Пока ничего не устанавливай, не оплачивай и не публикуй.
```

**Что должно получиться:** Выбранный подход и понятный план размещения.
Для GitHub Pages сайт Next.js должен допускать статическую сборку;
встроенная серверная обработка и стандартная оптимизация изображений требуют
другого решения или отдельной настройки.

### Промпт 11. Сайт или Storybook не запускается

**Когда использовать:** Получил ошибку запуска, пустую страницу или открыл старую версию.

**Что приложить:** Текст ошибки или скриншот и путь к папке проекта.

```text
Разберись, почему [сайт или Storybook] не запускается в [путь проекта].
Ошибка: [текст или скриншот]. Проверь папку проекта, требуемую версию Node.js,
зависимости и результат npm run setup. Изучи реальные ошибки, не угадывай причину.
Если порт занят, используй свободный и дай правильный адрес. Если показана
старая версия, найди относящийся к проекту сервер и обнови просмотр.
Сохрани мои изменения, локальные навыки и файл закреплённых версий зависимостей.
Не сбрасывай проект и не обновляй все зависимости без необходимости.
Исправь подтверждённую причину и проверь запуск. Объясни результат простыми словами.
```

**Что должно получиться:** Рабочий запуск или конкретная подтверждённая причина блокировки. Обычные адреса: сайт — порт 3000, Storybook — 6006; при занятости можно использовать другие.

### Промпт 12. Проверить обновление пака для старого проекта

**Когда использовать:** Ты улучшил свой шаблон или Маис обновил исходный стартер, а клиентский проект уже содержит собственные страницы и правила.

**Что приложить:** Папку клиентского проекта и ссылку на новую версию пака.

```text
Сравни наш проект [папка] с новой версией пака [ссылка или версия].
Работай только на чтение. Выдели полезные исправления и изменения правил,
навыков, зависимостей и настройки. Покажи конфликты с нашим кодом и решениями.
Подготовь план переноса: что взять, что пропустить, какие файлы затронет
каждый шаг и как проверить результат. Не заменяй проект новой копией шаблона
и не перезаписывай наши AGENTS.md, страницы или дизайн-систему.
Реализацию обновления начнём после выбора конкретных изменений.
```

**Что должно получиться:** План выборочного обновления. Изменения исходного шаблона автоматически в клиентский проект не попадают.

## GitHub: рабочие сценарии

Обычно один клиентский сайт хранится в одной отдельной папке и одном
репозитории. Агент сам спросит, в какой репозиторий сохранять, или
предложит создать новый приватный — если на компьютере выполнен вход
в GitHub через `gh`. Отправляет только по твоей просьбе. Для начала не нужны дополнительные ветки на каждую мелочь.
Большое изменение или эксперимент удобнее отделить от основной версии.

Обычный цикл: задача → изменения → просмотр результата → коммит → отправка
на GitHub. После утверждения эксперимент можно объединить с основной веткой.
Публикация сайта настраивается отдельно и иногда запускается автоматически.

Codex и Claude могут работать с одной папкой по очереди. Перед передачей
сохраняй текущий статус в документах проекта: Git хранит файлы, а не память
агента. Для одновременной работы нужны отдельные рабочие копии, а не просто
два агента, переключающих ветки в одной папке. GitHub и GitHub Pages — разные
вещи; публичный репозиторий делает загруженные файлы доступными всем.

### Промпт 13. Сохранить проект на GitHub

**Когда использовать:** Проект есть на компьютере, нужно впервые связать
его с твоим репозиторием и отправить файлы.

**Что приложить:** Путь к проекту и ссылку на твой репозиторий. Для клиентских
материалов заранее выбери нужную видимость: private (только с доступом)
или public (для всех). Ссылку на чужой шаблон не используй как место отправки.

```text
Подготовь проект [папка] для моего репозитория [ссылка GitHub].
Сначала проверь местные изменения, историю Git, связь с GitHub и содержимое
репозитория. Если в папке смешаны проекты, собери этот проект отдельно;
если история уже есть, сохрани её. Не создавай второй Git внутри проекта.
Включи нужные исходники и материалы; исключи секреты, временные файлы,
установленные зависимости и ненужные сборки. Для статического сайта включи
файлы, необходимые выбранному способу публикации. Проверь .gitignore
(список исключений); он сам не удаляет уже сохранённые файлы из истории.
Добавь короткую инструкцию по запуску и обновлению. Проверь результат,
сохрани нужные изменения коммитом (версией в истории) и отправь на GitHub.
Если удалённый репозиторий уже содержит другую работу, не перезаписывай её:
покажи расхождения и предложи план. Если нужен вход, объясни, что мне сделать.
Сайт пока не публикуй. Если отправка запускает автоматический выпуск,
сообщи об этом до отправки и дождись моего решения о выпуске.
```

**Что должно получиться:** Нужные файлы и история в твоём репозитории,
ссылка на коммит и понятная инструкция.

### Промпт 14. Проверить и сохранить текущий этап

**Когда использовать:** Доработка готова и ты хочешь сохранить её как этап.

**Что приложить:** Какие изменения относятся к этапу и нужно ли отправлять
их на GitHub прямо сейчас.

```text
Проверь состояние Git в [проект]: текущую ветку, изменённые файлы и связь
с GitHub. Этап: [что сделано]. Покажи короткий список изменений и проверь
затронутый результат. Не включай постороннюю работу и секреты.
Если всё в порядке, создай коммит (сохранённую версию) с понятным названием.
Отправка на GitHub: [да или нет]. Перед отправкой проверь, запускает ли она
публикацию сайта; если да и выпуск не утверждён, остановись перед отправкой.
Сообщи ветку, коммит, какие проверки выполнены и дошли ли изменения до GitHub.
```

**Что должно получиться:** Сохранённый этап и ясный статус. Коммит не
обязательно является финально утверждённым результатом — можно сохранять
и промежуточную работу, обозначая это в названии.

После отправки GitHub сам проверяет код и собирает сайт (GitHub Actions —
автоматическая проверка). Зелёная галочка рядом с коммитом — всё прошло.
Красный крестик — попроси агента: «Проверка на GitHub не прошла, найди
причину и исправь».

### Промпт 15. Попробовать изменение в отдельной ветке

**Когда использовать:** Хочешь новый вариант меню, большой блок или другую
идею, которую ещё не утвердил.

**Что приложить:** Задачу, исходную версию и критерии результата.

```text
Подготовь отдельную ветку Git для эксперимента [задача] от [утверждённая
ветка или версия]. Сначала проверь местные изменения; не потеряй их
и не перенеси случайно в эксперимент. Если разделение неоднозначно,
покажи варианты до переключения. Создай ветку с понятным названием.
Сделай [изменения], проверь результат и дай способ просмотра.
Эксперимент пока не объединяй с основной веткой и не публикуй.
Сохрани проверенный этап коммитом. Сообщи, как вернуться к основной версии,
и где записаны решения для продолжения работы.
```

**Что должно получиться:** Отдельная история эксперимента и результат для
сравнения. В одной папке переключение веток меняет её файлы; если нужно
смотреть две версии одновременно, попроси отдельную рабочую копию.

### Промпт 16. Утвердить ветку и перенести в основную версию

**Когда использовать:** Эксперимент проверен, выбранный вариант утверждён.

**Что приложить:** Название ветки, что именно утверждено, целевую ветку
и нужно ли выпускать результат на сайт.

```text
Утверждены изменения [список] из ветки [название]. Перенеси их в [main
или другая основная ветка]. Сначала проверь различия, актуальность веток
и местные изменения. Если ветка содержит лишнее, перенеси только утверждённое.
Конфликты (разные правки одного участка) разрешай по утверждённому результату;
если выбора нет в материалах, покажи конкретный вопрос.
Проверь результат после объединения. Не удаляй рабочую ветку.
Отправка на GitHub: [да или нет]. Выпуск сайта: [разрешён или пока нет].
Если отправка автоматически выпускает сайт и выпуск не разрешён, не отправляй
в публикуемую ветку. Сообщи итоговую версию и статус отправки и публикации.
```

**Что должно получиться:** Основная версия содержит утверждённые изменения.
Если проект требует PR (запрос на объединение), подготовь его вместо обхода
правил и дождись предусмотренного проектом одобрения.

### Промпт 17. Продолжить с другого компьютера или агента

**Когда использовать:** Переходишь на другой компьютер или открываешь тот же
проект в Claude после Codex либо наоборот.

**Что приложить:** Репозиторий, нужную ветку, папку и документ текущего статуса.
Перед передачей работы сохрани контекст по промпту 2а.

```text
Продолжи проект [репозиторий] в [папка], ветка [название].
Если местной копии нет, клонируй репозиторий (скачай файлы с историей Git).
Если она есть, сначала проверь несохранённые изменения и местные коммиты.
Забери обновления с GitHub, сохранив мою работу; не сбрасывай папку ради
совпадения с удалённой версией. При расхождениях покажи их и предложи решение.
Прочитай действующие инструкции и [документ статуса], проверь настройку
проекта после смены пути. Укажи недостающие зависимости и доступы,
не запрашивая секреты в открытом чате. Запусти нужный просмотр и сообщи
актуальную ветку, версию, что готово и следующий шаг. Сайт пока не меняй.
```

**Что должно получиться:** Актуальная рабочая копия и восстановленный
контекст. GitHub не переносит установленные программы, секретные настройки,
подключения инструментов или историю чатов автоматически.

### Промпт 18. Отменить конкретное неудачное изменение

**Когда использовать:** Нужно вернуть старое меню или убрать неудачную
правку, сохранив остальные изменения.

**Что приложить:** Какой участок вернуть, как должна выглядеть версия
и что обязательно сохранить. Если знаешь коммит — укажи его.

```text
Отмени только [конкретное изменение] в [проект]. Нужный результат: [описание
или версия]. Обязательно сохрани [остальные изменения].
Сначала проверь, где правка находится: только в файлах, в местном коммите
или уже на GitHub. Сохрани восстановимую копию затрагиваемой местной работы.
Выбери способ, сохраняющий остальную работу. Для отправленной истории
предпочти новый отменяющий коммит; не переписывай опубликованную историю
и не используй принудительную отправку без отдельного согласования.
Если отмена затронет другие изменения, покажи это до выполнения.
Проверь нужный участок после отмены. Пока не отправляй на GitHub и не выпускай сайт.
```

**Что должно получиться:** Конкретная правка отменена, полезная работа
сохранена. Возврат всего проекта к старому состоянию — более широкая задача.

## Ежедневный короткий порядок

1. Открой папку **этого клиента** в Claude Code или Codex.
2. Дай новую задачу и её источник: макет, текст клиента или референс.
3. Уточни, утверждены ли новые сведения или это пока идея.
4. Попроси обновить нужные файлы **и видимый сайт**, если информация должна
   появиться на страницах.
5. Посмотри результат в браузере. Для повторяющихся элементов открой
   Storybook.
6. Перед сдачей попроси выполнить промпт проверки. Отдельный аудит и
   публикацию заказывай отдельно.

Локальный сайт обычно открывается по `http://localhost:3000`, Storybook —
по `http://localhost:6006`. Команды запуска: `npm run dev` и
`npm run storybook` в двух отдельных терминалах. `localhost` означает,
что ты открываешь локальный просмотр; сам запуск не публикует сайт
в интернете.

## Что важно помнить

- Макет Figma требует доступа агента (через figma-console) к конкретному файлу. Если figma-console не отвечает, агент попробует запасные подключения и скажет, какое использовал.
- При установке npm может писать о «уязвимостях» в инструментах сборки. Это известно и не влияет на сайт. Не запускай `npm audit fix --force`: он откатывает Next.js на старую версию. Наличие шаблона
  само этот доступ не создаёт.
- Демонстрационные салатовый цвет, шрифт Manrope и картинки нужно заменить
  для клиента.
- Скриншот показывает только видимое состояние: точный шрифт, мобильную
  версию и поведение при наведении иногда приходится уточнять.
- Новые проекты не получают обновления шаблона автоматически.
- Язык сайта по умолчанию английский; другой язык укажи в стартовом запросе.
- Переходишь между Claude и Codex — сохрани состояние промптом 2а.

## Глобальные сценарии и независимая проверка

Это личное дополнение: глобальные навыки `project-design-workflow` и
`site-component-system` на твоих компьютерах (в Claude и в Codex). В шаблон
они не входят; на новом компьютере их нужно поставить отдельно. Контекст
самого клиента хранится в его проекте и переносится вместе с папкой.

### Что включено

- `site-component-system` помогает создать или обновить Storybook из реальных
  элементов сайта. Он учитывает устройство проекта и не вводит сам шаг 8px.
  В проекте из этого пака его собственные обязательные правила сохраняются.
- `project-design-workflow` помогает разобрать материалы, собрать или обновить
  систему по утверждённому источнику и подготовить передачу работы.
- После завершения крупного этапа сайта правила предусматривают отдельного
  проверяющего, если доступны инструменты агентов. Проверка не доказывает
  автоматически, что клиент одобрил дизайн.

Можно писать обычными словами. Если новый навык пока не появился в списке,
открой новый чат и проверь его наличие. Явное имя ниже помогает выбрать
нужный сценарий, но наличие файлов навыка не гарантирует доступ к Figma или браузеру.

### Разобрать бэкап

Используй при переносе старого проекта или большой папки материалов.

```text
Используй project-design-workflow. Изучи материалы клиента в [папка].
Составь краткий список источников и перенеси полезную информацию в существующие
документы проекта. Отдели утверждённое от черновиков, покажи противоречия
и то, что не удалось прочитать. Оригиналы оставь на месте. Сайт пока не меняй.
```

### Создать или обновить систему

Используй после утверждения концепта, главной страницы или набора страниц.

```text
Используй project-design-workflow. Утверждённый источник: [ссылка или файл].
Создай/обнови дизайн-систему в [Figma / коде / обеих средах] на основе этого
источника. Используй существующие общие стили и элементы. Отдели решения
из источника от предложенных дополнений. Обнови карту системы и проверь
затронутые страницы. Storybook [обнови существующий / создай / не добавляй].
```

Если нужен только документ с правилами, так и напиши: «Подготовь описание
дизайн-системы, код и Figma пока не меняй». Для переноса из сайта в Figma
или обратно укажи направление и утверждённую версию. Одновременная
автоматическая синхронизация сама по себе не включается.

### Создать или обновить Storybook

Используй для отдельного каталога общих элементов и их состояний.

```text
Используй site-component-system. Создай/обнови Storybook для [проект].
Покажи реальные общие компоненты сайта, их поддерживаемые состояния
и основы оформления. Сохрани утверждённый дизайн и текущие технологии.
Проверь работу каталога и затронутых страниц, сообщи ограничения.
```

### Сохранить состояние и продолжить

Перед новым чатом или переносом папки:

```text
Используй project-design-workflow. Сохрани актуальное состояние проекта
в существующий документ передачи работы: что сделано, что утверждено,
какие источники главные, какие проверки реально выполнены, что осталось
и с чего продолжить. Отметь незакоммиченные изменения и настройки,
которые потребуются на другом компьютере. Секреты в документ не записывай.
```

В новом чате или на другом компьютере:

```text
Используй project-design-workflow. Прочитай правила проекта и актуальную
передачу работы. Сверь её с текущими файлами и доступными инструментами.
Коротко сообщи состояние и продолжи [задача]. Исторические логи читай
только если в актуальных документах не хватает конкретной информации.
```

### Когда запускается независимая проверка

| Изменение | Проверка |
| --- | --- |
| Опечатка, отдельный отступ, небольшое исправление | Затронутый элемент и связанное поведение; без отдельного агента |
| Завершённая новая страница или пользовательский путь | Независимое ревью этапа |
| Большой редизайн или общие компоненты для нескольких страниц | Независимое ревью затронутых страниц и состояний |
| Твой прямой запрос | Проверка в указанном объёме |

Проверяющий сначала пишет замечания и не меняет код. При сборке сайта основной
агент исправляет подтверждённые ошибки в рамках задачи; если ты попросил только
ревью, результатом будет отчёт. После исправлений перепроверяются проблемы
и связанные участки. Если отдельного агента или браузера нет, агент должен
сообщить, какая часть проверки не выполнена независимо или визуально.

Это ревью выполняет роль финальной проверки этапа, а не запускает два полных
аудита подряд. Отдельный финальный аудит шаблона `site-audit` по-прежнему
заказывается явно, как в промпте 8. Обязательные проверки проекта сохраняются
даже при небольшой правке.

Ручной запрос:

```text
Проведи независимое ревью завершённого этапа: [страница или набор изменений].
Используй отдельного агента-проверяющего (в Codex — отдельную сессию). Сравни результат с утверждённым
макетом и правилами проекта. Проверь удобство интерфейса, мобильную версию,
состояния элементов и работу основных действий.

Код пока не меняй. Для каждой подтверждённой проблемы укажи место, важность,
ожидаемый и фактический результат, приложи доступные доказательства.
Предложения по улучшению отдели от ошибок.

После исправлений перепроверь только найденные проблемы и связанные
с ними участки.
```
